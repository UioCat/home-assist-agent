# 统一前端与双后端本地运行设计

日期：2026-08-05

状态：待实现

## 目标

把当前主流程前端和 `modules/iot-mcp` 设备控制前端合并为一个 React 单页应用，同时保持两个 FastAPI 后端在进程、端口、数据存储和生命周期上互相独立。

本地运行固定使用以下入口：

| 服务 | 地址 | 职责 |
| --- | --- | --- |
| 统一前端开发服务器 | `http://127.0.0.1:5173` | 页面、路由和本地 API 转发 |
| Home Assist Agent | `http://127.0.0.1:8080` | 指令、健康状态和主流程审计 |
| IoT MCP | `http://127.0.0.1:8090` | 设备、物模型、Provider、操作、事件和 IoT 审计 |

两个后端不进行服务发现、反向代理或后端到后端调用。任一后端不可用时，另一后端仍可独立启动并对外提供自己的接口。

## 采用方案

以 `modules/iot-mcp/web` 为唯一活动前端，将当前根目录 `frontend` 的家庭指令中心、主流程健康状态和审计中心迁入该应用。原因如下：

- IoT 前端已经具有完整的 TypeScript、React Router、响应式侧栏和页面状态测试基础。
- 设备实例、物模型、Provider 等页面数量更多，迁移较小的主流程页面可以降低合并风险。
- 不使用 iframe，不保留两套运行时导航和重复的 React 应用状态。

根目录旧前端在迁移验证完成后不再作为活动入口。其可复用组件会被移植而不是运行时引用，避免形成跨 package 的隐式耦合。

## 页面信息架构

统一侧栏按用户任务而不是后端归属组织：

1. 家庭指令中心：默认首页 `/`
2. 审计中心：`/audit`
3. 家庭概览：`/overview`
4. 设备实例：`/devices`
5. 物模型：`/thing-models`
6. 操作与确认：`/operations`
7. 设备事件：`/events`
8. Provider：`/providers`
9. 消息通道：`/message-channels`

设备详情继续使用 `/devices/:deviceId`。原 IoT 概览从 `/` 调整到 `/overview`，旧的根路由不再指向设备概览。

统一界面沿用当前 IoT 控制台的侧栏、IBM Plex 字体、深色石墨色画布、蓝色结构色和状态色。家庭指令中心的执行轨迹和审计内容会适配这套视觉 token，不并存第二套顶栏和颜色系统。

## 前端结构

统一应用继续由一个 `BrowserRouter` 管理。应用内部拆分为两个 API 客户端：

- `AgentApiClient`：负责 `/api/commands`、`/api/health`、`/api/audit`。
- `HttpApiClient`：保留 IoT MCP 的 `/api/v1` 接口。

开发环境由 Vite 使用不冲突的浏览器侧命名空间：

- `/agent-api/*` 转发到 `http://127.0.0.1:8080/api/*`。
- `/api/v1/*` 转发到 `http://127.0.0.1:8090/api/v1/*`。

这样前端请求保持同源，不需要在本地开发模式扩大后端 CORS。构建版本由 IoT MCP 的 `8090` 静态托管；构建时 Agent API 基地址显式设为 `http://127.0.0.1:8080/api`，根后端只允许来自本机 `8090` 的受限 CORS 请求。IoT API 保持同源 `/api/v1`。

API 基地址必须可通过 Vite 环境变量覆盖，但默认仅允许本机地址，文档不记录或回显任何 HA Token、Cookie、密码或其他凭据。

## 会话和降级行为

IoT MCP 当前本地免鉴权模式保持不变。统一前端启动时分别探测两个后端：

- Agent 后端不可用：侧栏和设备模块仍可使用；家庭指令中心显示局部错误，不阻断整个应用。
- IoT 后端不可用：家庭指令与主流程审计仍可使用；IoT 页面显示现有加载失败状态。
- 两者都可用：各自状态在侧栏底部独立展示，不能用一个“已连接”状态代表两个服务。

前端不得把任何凭据写入 localStorage、sessionStorage、URL 或日志。

## 审计和消息标识

两个后端继续写入各自的追加式审计存储，不合并数据库，也不引入跨后端查询依赖。

- 家庭指令提交前，前端生成唯一 `message_id`，请求中的兼容字段 `request_id` 如存在必须与其相同。
- Agent 后端继续用该 ID 串联用户输入、Codex、HA MCP、失败分支和最终响应。
- IoT HTTP 请求继续由 IoT 中间件生成唯一 `message_id`，并返回一致的 `X-Message-ID` 与 `X-Request-ID`。
- 统一审计页面第一期只展示 Agent 审计链；IoT 操作和事件仍在现有 IoT 页面查看，避免假装两个独立账本已有统一事务语义。

所有错误提示只显示可公开的状态、错误码和脱敏信息。

## 设备控制与高风险边界

本次合并不改变控制策略：

- 用户在设备页面点击开关、滑块或服务按钮属于明确人工交互，包含门锁等高风险设备时也直接执行，不增加二次确认。
- 只有 AI 对模糊指令作出自主决策，或 AI 根据事件自主判断并准备执行高风险动作时，才进入二次确认。
- 前端不能仅根据设备风险等级拦截人工操作。

## 统一启动

新增仓库级本地启动器，一次启动三个长期进程：

1. 根项目虚拟环境中的 Home Assist Agent，端口 `8080`。
2. `modules/iot-mcp/backend` 的 IoT MCP HTTP 服务，端口 `8090`。
3. `modules/iot-mcp/web` 的 Vite 服务，端口 `5173`。

启动器负责：

- 从根目录本地 `.env` 读取运行配置，并仅在子进程内把 HA URL/Token 映射为 IoT MCP 对应变量。
- 不打印、持久化或写入审计任何凭据值。
- 为两个后端使用独立 SQLite 数据库和审计数据库路径。
- 在 `Ctrl+C` 或任一子进程异常退出时终止同组其余子进程，避免遗留孤儿进程。
- 启动前检查 Python、uv、Node 依赖和端口占用，错误信息给出具体修复命令。

启动器是进程编排工具，不把两个后端导入同一个 Python 进程，也不改变它们各自的配置入口。

## 测试策略

实现使用测试驱动流程，先增加失败测试再修改生产代码。

前端测试覆盖：

- `/`、`/audit`、`/overview` 和现有 IoT 路由的渲染与导航。
- Agent 与 IoT API 客户端使用正确的独立基地址。
- 一个后端失联时，另一个模块仍保持可操作。
- 指令提交携带唯一 `message_id`，响应轨迹和审计查询正确显示。
- 人工高风险设备操作不出现二次确认拦截。

后端测试覆盖：

- Agent 的受限本地 CORS 配置不放开任意来源。
- 两个后端的健康接口分别在 `8080` 和 `8090` 可访问。
- IoT API 仍保持现有人工直控和自主高风险确认边界。
- 审计不可用时，外部副作用调用仍被阻断。

启动器测试覆盖：

- 命令构造、环境变量映射和凭据不进入输出。
- 端口冲突和缺少依赖时快速失败。
- 子进程退出和信号转发能清理其余进程。

最终验证执行两个 Python 测试套件、统一前端测试、TypeScript 检查、生产构建，并真实启动三个端口完成健康检查和关键页面冒烟测试。

## 非目标

- 不合并两个 FastAPI 应用、依赖注入容器或数据库。
- 不让 Agent 后端代理 IoT API，也不让 IoT 后端代理 Agent API。
- 不在本次实现中统一两个审计数据库或建立跨库事务。
- 不恢复 IoT Web 鉴权。
- 不改变 HA 作为 IoT 设备来源之一的同步、离线、删除和设备类型筛选规则。
- 不新增高风险人工操作确认。

## 验收标准

- 用户只需打开一个前端入口即可使用家庭指令、审计和全部 IoT 页面。
- 单一命令可启动 `5173`、`8080`、`8090`，并可用 `Ctrl+C` 完整停止。
- 停止任一后端不会导致另一个后端退出。
- 页面请求明确发送到对应端口，没有后端间运行时依赖。
- 现有 HA 真实设备同步和人工设备控制可继续工作。
- 测试、类型检查和构建全部通过，审计与凭据脱敏约束不回退。
