# IoT 设备离线态、类型筛选与 HA 消失设备收敛设计

日期：2026-08-02
状态：待书面复核

## 1. 背景

“设备实例”页面已经使用家庭 App 风格的设备卡片展示来自 Home Assistant 等 Provider 的真实设备，并支持卡片主操作。但当前卡片 DTO 没有标准化设备类型和设备级可用性：用户不能按灯具、插座等物理类型快速筛选；HA 实体为 `unavailable` 时可能仍看起来像普通关闭态；HA 全量清单中消失的设备会保留为 `missing` 卡片。

此外，HA 灯关闭后可能返回 `brightness: null`。现有映射仅检查属性键是否存在，随后尝试把 `null` 转为浮点数，导致控制后的状态校验和 WebSocket 状态回写中断。该缺陷会让真实设备已经关闭，但卡片继续显示旧的开启状态。

## 2. 已确认目标

- 采用后端标准化方案：Provider 负责提供物理设备类型和可用性，前端不根据显示名称自行猜测。
- 搜索框下方展示当前全部设备类型，支持一键快捷筛选。
- 设备类型、文字搜索和运行状态筛选可以组合使用。
- 离线设备整卡置灰、显示“离线”文字并禁用快捷控制，但仍允许进入详情查看诊断信息。
- HA `unavailable` 判定为离线；`unknown` 只判定为状态未知，不等同于离线。
- 原本由 HA 同步、后来从 HA 权威清单中消失的设备，从当前设备列表和可控制目标中移除。
- 被移除设备的操作与审计历史必须保留；设备以后以相同 HA 身份重新出现时恢复原设备身份。
- 修复 `brightness: null` 导致关闭状态无法回写的问题。
- 保持人工交互和 AI 自主操作的高风险确认边界不变。

## 3. 非目标

- 不允许前端通过名称正则独立决定设备类型。
- 不向用户直接暴露 HA 的原始 entity domain、model token 或内部 entity ID 作为筛选标签。
- 不硬删除操作、设备事件或审计历史。
- 不把 Provider 整体 degraded 直接等同于每台设备离线。
- 不在本次加入多类型并选、收藏、排序配置或用户自定义类型。
- 不改变卡片主要控制能力的选择规则和人工高风险直接执行策略。

## 4. 方案比较

### 方案 A：Provider 标准化，卡片 DTO 直接返回类型与可用性（采用）

HA Adapter 根据设备注册表、非配置实体、model 和 domain 生成标准类型；其他 Provider 使用相同标准类型契约。同步和事件链维护设备可用性，卡片 DTO 直接输出标准字段。

优点是语义稳定、前端简单、可扩展到其他 Provider，也能正确识别“名称叫电脑、物理上是插座”的设备。缺点是需要扩展 Provider 标准化模型和同步测试。

### 方案 B：前端按名称和能力推断

优点是后端改动少。缺点是同一名称在不同家庭含义不同，重命名会改变类型；Provider 原始语义无法复用，误分类不可避免。

### 方案 C：前端直接使用 HA domain/model

优点是保留原始信息。缺点是 `light + switch` 等复合设备会产生技术型标签，并把通用设备页面绑定到 HA，不适合后续多 Provider。

## 5. 标准设备类型

Provider 输出稳定的 `device_type` ID，HTTP DTO 同时返回可本地化展示的 `device_type_label`。首批标准类型：

| ID | 展示名称 | 典型设备 |
| --- | --- | --- |
| `light` | 灯具 | 灯、灯带、显示器挂灯 |
| `outlet` | 插座 | 智能插座、排插 |
| `climate` | 温控 | 空调、恒温器 |
| `heater` | 取暖器 | 电暖器、暖风机 |
| `humidifier` | 加湿器 | 加湿器 |
| `lock` | 门锁 | 智能门锁 |
| `appliance` | 家电 | 电磁炉等独立家电 |
| `switch` | 开关 | 不能进一步识别的开关设备 |
| `other` | 其他 | 无法识别的设备 |

HA 分类按以下优先级执行：

1. HA 注册表或未来 Provider 显式给出的标准物理类型。
2. `device_registry.model` 和设备名称中稳定的产品类别词，例如 `plug/outlet/插座`、`lamp/light/灯`、`heater/取暖`、`humidifier/加湿`、`cooker/电磁炉`、`lock/锁`。
3. 排除 `entity_category=config` 后的主要实体 domain：`lock`、`climate`、`light`、`switch`。
4. 无法识别时使用 `other`。

名称只作为 HA Adapter 后端分类的低优先级补充，标准化结果随 binding metadata 持久化；前端不重复规则。类型 ID 稳定，展示文案可以独立调整。

## 6. 设备可用性

标准可用性为：

- `online`：至少一个非配置、可控制的主要实体有有效状态。
- `offline`：设备存在于 HA 注册表，但全部非配置、可控制主要实体均为 `unavailable`。
- `unknown`：无法获得可靠状态，或主要实体仅返回 `unknown`。

`DeviceProvider` 的发现状态和 `ProviderEvent` 都携带设备级可用性。HA Adapter 在首次发现时建立设备到主要实体的状态表；收到 `state_changed` 后更新对应实体，再计算整个物理设备的可用性。单个配置实体或诊断实体不可用，不应把整个物理设备标为离线。

可用性通过设备本地投影持久化：在线设备保持 `active`，离线设备使用 `offline`，状态未知使用 `unknown`。`provider_status` 继续表示整个 Provider 的健康状况，不能替代设备级状态。

HA 状态映射必须把 `unavailable` 与普通 `off` 分开；灯关闭后的 `brightness: null` 不生成 Brightness 数值，但必须保留 `PowerSwitch=false`，并继续完成控制校验和事件写回。

## 7. HA 消失设备的软移除

HA 全量设备清单是该 Provider 当前库存的权威来源。每次成功完成全量同步后：

1. 找出之前属于 HA、这次未出现的 binding。
2. 把对应设备状态标记为 `missing`，表示已从当前库存软移除。
3. 当前设备列表、卡片接口、类型统计和控制目标查询都排除 `missing` 设备。
4. 保留设备记录、稳定 binding、属性历史、事件、操作和审计链，不执行物理删除。
5. 相同 `external_device_ref` 以后重新出现时，复用原 device ID，并恢复为 `active`、`offline` 或 `unknown`。

只有 Provider 全量同步成功后才能执行缺失收敛。HA 超时、认证失败或注册表读取失败时不得误删现有设备。

## 8. 卡片接口

`GET /api/v1/device-cards` 扩展字段：

```json
{
  "device_id": "...",
  "display_name": "书桌灯",
  "device_type": "light",
  "device_type_label": "灯具",
  "availability": "offline",
  "device_status": "offline",
  "provider_status": "healthy",
  "primary_control": null
}
```

规则：

- `device_type` 和 `device_type_label` 来自 Provider 标准化 metadata。
- `availability` 明确表达 `online/offline/unknown`。
- `missing` 设备不返回卡片。
- 离线设备可以保留最后一次已知值用于详情诊断，但卡片状态摘要必须优先显示“离线”，不能用旧值显示“开启”。
- 离线、unknown 或 missing 设备不提供可执行的卡片快捷操作；完整控制服务仍需在执行前验证当前设备可控性。

## 9. 页面与交互

### Intent

用户刚进入家庭设备页时，需要立即回答三个问题：家里有哪些设备、哪些设备不可达、如何快速缩小到某一类设备。页面应保持苹果家庭 App 式的平静和低认知负担。

### Domain

家庭附件、房间、在线信号、设备类别、触达能力、最后状态、快速控制、设备清单。

### Color world

石墨画布、深蓝灰设备面板、电气蓝交互信号、暖琥珀开启态、低饱和绿在线信号、灰烬色离线态。颜色只表达状态和选择，不新增装饰性颜色。

### Signature

搜索框下方增加“家庭附件类型轨道”：一排带类型名称和数量的紧凑按钮，将家庭库存变成可扫视的附件索引。桌面保持单行，窄屏水平滚动。

### Rejecting defaults

- 不使用第二个下拉框隐藏类型，而使用始终可见的类型轨道。
- 不只用全卡 opacity 表达离线，而使用灰阶表面、离线文字、状态图标和禁用控件共同表达。
- 不在前端用设备名称正则分类，而使用 Provider 标准字段。

### 组件层级

1. 页面标题。
2. 文字搜索与运行状态筛选。
3. 类型轨道。
4. 设备数量和区域分组。
5. 设备卡片。

类型轨道包含：

- `全部 N`，始终位于首位。
- 当前有效库存中实际存在的每种类型，按固定产品顺序排列并显示数量。
- 原生 `<button>`，使用 `aria-pressed` 表达当前选择。
- 44px 最小点击高度、清晰的 focus ring 和 active 状态。
- 类型选择、文字搜索、运行状态三者取交集；清空文字搜索不会清空类型。
- 若同步后当前选择类型不再存在，自动回到“全部”。

类型数量基于全部当前可见库存计算，不随文字搜索变化，避免用户输入时按钮跳动。`missing` 设备不计数，离线设备计入其物理类型。

### 离线卡片

- 使用独立 `device-card--offline` 状态，不与普通关闭态混淆。
- 卡片背景、边框、图标和元数据统一降饱和，主标题仍保持可读对比度。
- 状态摘要固定为“离线”，并显示最后更新时间。
- 快捷控制按钮禁用，`aria-label` 说明设备离线不可控制。
- 卡片主体仍可进入详情页。
- 不只依赖颜色表达离线。

视觉继续使用现有 IBM Plex Sans / Mono、4px 间距基准和边框色块深度策略，不引入新字体、渐变或阴影体系。

## 10. 控制与安全边界

- 页面主动点击在线设备仍是 `human_interactive`。
- 包括门锁在内的人工明确操作，通过能力校验后直接执行，不增加二次确认。
- 只有 AI 模糊决策或基于事件自主判断的高风险操作需要二次确认。
- 离线、unknown、missing 设备在进入 Provider 副作用前拒绝控制，并返回明确、可审计且不可误认为成功的结果。
- 控制请求、HA 外部调用、事件同步和错误分支继续共用唯一 `message_id`，兼容 `request_id` 与其相同。

## 11. 数据流

### 首次与周期同步

1. HA Adapter 获取注册表、状态与服务。
2. 为每个物理设备计算标准类型和可用性。
3. `DeviceSyncService` 更新设备、binding、模型和快照。
4. 同步完整成功后，软移除本轮缺失的 HA 设备。
5. 卡片接口只读取本地投影，不额外访问 HA。

### 实时事件

1. HA WebSocket 接收 `state_changed`。
2. Adapter 更新实体状态并生成包含设备可用性的 `ProviderEvent`。
3. 容器用同一事件 `message_id` 写入设备状态、属性快照和设备事件。
4. 下次卡片查询读取已更新投影。

无关或不受支持的 HA 实体事件应被安全忽略，不能把 Provider 标为 degraded，也不能终止订阅。

## 12. 测试策略

### 后端 RED/GREEN 用例

- `brightness: null` 的关闭灯状态生成 `PowerSwitch=false`，不抛异常且不生成无效 Brightness。
- HA `unavailable`、`unknown` 和普通 `off` 映射为不同可用性。
- 物理设备只有配置实体不可用时仍保持 online；全部主要实体 unavailable 才 offline。
- 插座、灯具、取暖器、加湿器、门锁、家电和 fallback 类型按固定规则标准化。
- 卡片 DTO 输出类型、类型标签和 availability，且不返回 missing 设备。
- 成功同步后缺失的 HA 设备不可查询或控制，但历史操作仍存在。
- Provider 同步失败时不执行缺失软移除。
- 同一 HA 设备重新出现时恢复原 device ID。
- WebSocket 离线/恢复事件更新本地设备状态且不终止订阅。
- 无 binding 的不受支持实体事件被忽略，不把 Provider 标为 degraded。
- 审计链继续满足 `message_id == request_id`、请求/响应完整和凭据脱敏。

### 前端 RED/GREEN 用例

- 类型轨道展示“全部”和当前全部设备类型及数量。
- 点击类型后，只显示该类型设备；与文字和状态筛选取交集。
- 类型选择在清空搜索时保留，类型消失时恢复“全部”。
- 离线卡片显示离线文字、灰阶状态类并禁用快捷控制。
- unknown 设备显示状态未知，不使用 offline 状态类。
- missing 设备不会出现在页面数据中。
- 类型轨道具有 `aria-pressed`、键盘焦点和移动端可滚动结构。

### 验证

- 后端 pytest 与 Ruff 全绿。
- 前端 Vitest、TypeScript 与生产构建全绿。
- 使用真实 HA 只读验证类型分布和在线状态，不为验证主动操作设备。
- 在桌面和移动宽度检查类型轨道、离线卡片、长类型名称与空结果状态。

## 13. 验收标准

- 搜索框下方始终展示“全部”和当前实际存在的设备类型，可一键筛选。
- 类型、文字、运行状态三种筛选组合正确，数量稳定且不包含已移除设备。
- HA `unavailable` 设备在一次事件或同步后显示为离线，卡片置灰且无法快捷控制。
- HA `unknown` 不被误判为离线。
- HA 权威清单中消失的设备不再出现在列表和控制目标中，历史审计与操作仍可查询。
- 同一设备重新出现时恢复原身份。
- 灯关闭后 `brightness: null` 不再中断状态回写，卡片能显示关闭。
- 不受支持的 HA 事件不会令 Provider 降级或打断订阅。
- 人工高风险操作直接执行、AI 自主高风险操作二次确认的边界保持不变。
