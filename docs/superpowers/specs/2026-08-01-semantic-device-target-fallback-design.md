# Home Assist Agent 语义设备候选与混合自治设计

日期：2026-08-01

状态：已实现

## 1. 背景与问题

当前目标解析只把与用户称呼精确相等的个人术语、HA 名称、HA 别名或区域加入候选。
当用户说“打开床头灯”，而 HA 中只有“靠内灯”和“靠外灯”时，确定性候选为空，
编排器会跳过 Codex 目标解析并返回固定文案“没有找到可控制的目标，请换一种称呼”。

这保证了 Codex 不能编造实体，但也把安全边界错误地收窄成了字符串精确匹配：系统
已经拥有可控制设备事实，却无法据此推断或向用户提出具体问题。

本设计在不放宽实体身份、家庭边界、动作能力和审计约束的前提下，引入语义后备候选
和混合自治决策。

## 2. 已确认的产品规则

1. 精确名称、别名或已学习术语唯一命中时，保持现有直接执行流程。
2. 精确候选为空时，系统从同一家庭中生成有限的语义后备候选。
3. 唯一高置信度、低风险目标可以自动执行。
4. 存在多个合理目标时，不返回泛化的“换一种称呼”，而是使用真实设备名称定向询问。
5. 用户明确选择单个设备或“全部”后执行；完整成功后沿用现有术语学习流程。
6. 高风险动作继续由独立风险策略决定是否确认；目标语义置信度不能绕过风险策略。
7. 没有任何动作兼容设备，或 Codex 判断候选均不合理时，才返回未找到。
8. Codex 始终只能引用本次有限候选的 `candidate_id`，不能生成 `entity_id`。

## 3. 方案比较

### 方案 A：维持精确候选，只改善兜底文案

改动小，但系统仍不知道应该询问哪些真实设备，不能满足自行推理和定向澄清。

### 方案 B：将全部目录直接交给 Codex

推理空间最大，但噪声高、候选可能超限，也会削弱当前确定性边界，不采用。

### 方案 C：确定性资格过滤 + 语义后备候选 + Codex 排序

先按家庭、可用性、禁用状态、动作能力和显式设备类型提示做确定性过滤，再让 Codex
在有限候选内选择、判歧义或拒绝。该方案保留安全边界，同时提供足够推理空间，采用。

## 4. 候选生成

`CandidateBuilder` 分为两个阶段：

1. **精确阶段**：保持个人术语、家庭术语、HA 别名、HA 名称和区域的现有优先级。
2. **后备阶段**：仅当精确阶段没有候选时，从已通过 `_is_eligible` 的实体中生成单实体
   候选。

后备阶段使用以下确定性规则：

- 用户表达包含“灯”“灯光”“照明”等显式灯具提示时，只保留 `light` 域，避免插座、
  指示灯控制项和其他 `turn_on` 实体挤占候选。
- 没有可确定的设备类型提示时，保留所有动作兼容实体，但仍受
  `TARGET_CANDIDATE_LIMIT` 限制。
- 每个候选仍包含真实名称、区域、域、状态和目录版本；新增来源
  `semantic_fallback`，其规则权重低于所有精确证据。
- 排序必须稳定。后备候选优先考虑目标表达与名称的确定性文本相似度，再按
  `entity_id` 排序；文本相似度只用于裁剪候选，不直接授权执行。
- 不自动把任意多个后备实体合并成执行集合。

候选集非空后，现有 `CodexGateway.resolve_target` 继续执行。Prompt 明确要求：精确证据
缺失时，可以根据名称、区域、设备类型及用户原话做语义判断；只有一个明显目标时才
返回 `selected`，多个合理目标返回 `ambiguous`，都不合理时返回 `no_match`。

## 5. 混合自治与澄清

目标解析继续使用现有置信度阈值。`selected` 且达到阈值时进入刷新校验和风险策略；
否则进入澄清。

澄清响应由候选数据生成自然、具体的文案：

- 两个候选：`“床头灯”可能是“靠内灯”或“靠外灯”。你想打开哪一盏？也可以说“全部”。`
- 三个候选：列出三个名称并请用户选择；仅在这三个候选上接受“全部”。
- 一个低置信度候选：`你指的是“靠内灯”吗？`
- 无候选或 Codex 明确 `no_match`：说明未识别目标；如仍有安全的相关设备事实，可列出
  最多三个名称供用户改述。

澄清尝试保存明确展示的候选。用户后续输入支持：

- 现有的编号、`choice_id` 和完整设备名称；
- 候选名称的规范化表达；
- `全部`、`都打开`、`两盏都开` 等明确集合确认表达。

“全部”只合并本次已经展示并保存在澄清尝试中的候选，不扩展到家庭其他设备。合并后
仍经 `ResolutionVerifier` 刷新目录并逐项校验，不能绕过家庭、可用性、目录版本或动作
能力约束。

执行完全成功后，现有术语学习把原始表达映射到用户确认的单实体或稳定实体集合；
部分成功不学习。

## 6. 数据契约

保持 `TargetResolutionDecision`、`VerifiedTarget` 和 Codex 输出 Schema 不变。

扩展 `TargetCandidate.sources` 的允许语义值：

```text
semantic_fallback
```

若需要支持“全部”，编排器在澄清确认后基于原尝试中被展示的候选构造一个内部集合
候选。该候选必须：

- 只包含原尝试已展示候选的实体并集；
- 排序、去重且不超过 20 个实体；
- 继承原目录版本和 `home_id`；
- 作为本次确认消息的验证输入并写入审计；
- 不修改原历史审计事件或原解析尝试。

## 7. 审计与错误处理

所有新增路径沿用同一 `message_id`，兼容 `request_id` 与其相同。新增或扩展审计内容：

- `target.candidates_generated` 记录精确或后备生成模式及完整候选；
- Codex 请求完整记录后备候选和 prompt，响应记录结构化选择、stdout、stderr 和失败；
- 定向澄清的最终用户响应由现有 `user.response` 完整记录；
- “全部”确认记录被合并的候选编号和实体集合；
- 目录、MCP 或审计失败继续 fail closed；审计请求写入失败时不得调用外部副作用。

Authorization、Token、Cookie、API Key 等凭据仍在持久化前统一脱敏。

## 8. 测试与验收

按测试驱动方式覆盖：

1. “床头灯”精确无匹配，但存在“靠内灯”“靠外灯”时生成两个后备候选。
2. 显式“灯”提示不会把普通 `switch` 或不可用实体加入后备候选。
3. 后备候选仍受家庭、动作能力、禁用状态和数量上限约束。
4. 唯一后备候选被 Codex 高置信度选中后，刷新校验并执行真实 `entity_id`。
5. 多个合理候选返回包含真实设备名称的定向问题，不调用 MCP。
6. 用户选择单个设备后执行并学习原称呼。
7. 用户确认“全部”时只执行已展示候选，并学习稳定实体集合。
8. Codex 返回 `no_match` 时不执行设备。
9. 目录变化、低置信度、Codex 失败及审计失败保持 fail closed。
10. 审计测试验证成功、失败、脱敏和完整 `message_id` 链路。
11. 现有精确匹配、术语优先级、执行器和风险策略测试全部保持通过。

真实验收场景：HA 目录包含“靠内灯”和“靠外灯”，用户首次说“打开床头灯”时，系统
应点名询问具体设备；用户回答“全部”后仅打开这两盏，并在后续相同表达中自动解析到
这两个实体。

## 9. 不在本次范围

- 不引入向量数据库或外部 embedding 服务；
- 不修改风险等级和授权模型；
- 不让 Codex 访问候选集外的设备身份；
- 不自动修改 HA 中的实体名称、区域或别名；
- 不实现跨家庭或跨用户的自动术语共享。
